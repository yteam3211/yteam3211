Swerve Drive

Swerve drive is a drivetrain where each wheel module can both drive forward/backward and rotate to any steering angle. This lets the robot translate in any direction while also rotating, which is why swerve is so powerful in FRC.

Swerve is also one of the easiest systems to make confusing. The mechanical side must be built accurately, and the code side must be very careful with units, angles, offsets, and coordinate frames.

On our team, the swerve code is based on the CTRE Phoenix 6 default/generated swerve format. That means we do not expect new programmers to write all the low-level swerve math from scratch. We expect them to understand what the generated code represents, how to configure it, and how to debug it safely.

Drive Motor

Spins the wheel and controls how fast that module moves across the carpet.

Steer Motor

Rotates the wheel pod so the module points in the requested direction.

Absolute Encoder

Tells the code the real steering angle when the robot boots.

Gyro

Measures robot heading so drivers can use field-relative control and autos can estimate pose.

Mechanical Side

A swerve module is two mechanisms in one package. The wheel needs to spin, and the whole wheel assembly needs to turn. Good swerve code cannot hide bad mechanical assembly, so programmers should understand the hardware before tuning anything.

1. Module Layout

Each corner of the drivetrain has one swerve module. The code must know where each module is relative to the center of the robot.

  • Front left, front right, back left, back right: label modules clearly and keep the labels consistent in wiring, constants, code, and logs.
  • Wheelbase and track width: measure the distance between module centers, not the frame edges.
  • Center of rotation: normal driving rotates around the robot center, but advanced code can rotate around another point.

2. Drive System

The drive motor sends power through gears or belts to the wheel. The important code number is the conversion from motor rotations to wheel distance.

  • Wheel diameter: affects meters per wheel rotation. Worn wheels can change this slightly.
  • Drive gear ratio: converts motor rotations into wheel rotations.
  • Traction: wheel material, robot weight, and carpet condition affect acceleration and slipping.
  • Current limits: protect motors and reduce brownouts when all four modules accelerate hard.

3. Steering System

The steer motor points the wheel. This system must be precise because even a small angle error can make the robot drift, fight itself, or rotate unexpectedly.

  • Steer gear ratio: converts motor rotations into module angle.
  • Backlash: loose gears or belts can make the module angle lag behind the commanded angle.
  • Absolute encoder offset: the encoder's zero rarely matches the wheel's real forward direction, so every module needs its own offset.
  • Wheel alignment: all wheels should physically point the same direction when their code angle is zero.

4. CAN IDs And Wiring

Swerve has many devices. A four-module robot usually has eight motor controllers plus four steering encoders, before counting the gyro.

  • Write CAN IDs on the robot and in constants.
  • Keep drive motor, steer motor, and encoder IDs grouped by module.
  • Check that each module spins and steers from the correct corner before testing full drive code.
  • Use clear names in Phoenix Tuner, AdvantageScope, or dashboard logs so mistakes are obvious.

5. Mechanical Checks Before Code Tuning

  1. Put the robot on blocks.
  2. Command one module at a time.
  3. Verify the correct wheel spins.
  4. Verify positive drive direction is consistent across all modules.
  5. Verify positive steer direction is consistent across all modules.
  6. Set and record the absolute encoder offset for each module.
  7. Only then start full drivetrain testing on carpet.

Code Side

Swerve code turns a desired robot motion into four wheel speeds and four wheel angles. The core idea is simple: drivers ask for chassis movement, kinematics converts that request into module states, and each module controls its own drive and steer motors.

For our robot, this is usually wrapped by CTRE's Phoenix 6 swerve API and the project generated from Tuner X. Students should learn the shape of that generated code first, then learn how the math works underneath it.

1. Our CTRE-Based Format

The CTRE generated swerve project gives us a working structure with constants, drivetrain code, module configs, telemetry hooks, simulation support, and command-based integration. The most important pieces to recognize are:

  • TunerConstants: the generated constants file. This is where module IDs, encoder offsets, wheel locations, gearing, gains, and drivetrain constants usually live.
  • CommandSwerveDrivetrain: the subsystem-style drivetrain class used by command-based robot code.
  • SwerveDrivetrainConstants: robot-wide drivetrain settings, such as CAN bus name and Pigeon 2 ID.
  • SwerveModuleConstants: per-module settings for each wheel: drive motor, steer motor, CANcoder, offset, location, inversion, and module behavior.
  • CTRE swerve requests: objects used to command the drivetrain, such as field-centric driving, robot-centric driving, braking, and pointing wheels.

2. What Students Still Need To Understand

Generated code saves time, but it is not magic. If the constants are wrong, the robot will still drive wrong. Programmers should be able to explain what each generated value means and how it connects to the physical robot.

  • Module order: front-left, front-right, back-left, and back-right must match the real wiring.
  • CAN IDs: every TalonFX, CANcoder, and Pigeon 2 ID must match the robot.
  • Encoder offsets: every module needs the correct absolute encoder offset.
  • Module positions: X and Y locations are measured from the robot center.
  • Gains: steer and drive gains must be tuned for the real robot.
  • Control request: teleop code should use the CTRE request object that matches the desired driving mode.

3. Important Types

  • ChassisSpeeds: WPILib robot movement as vx, vy, and omega.
  • SwerveModuleState: WPILib representation of one module's target wheel speed and target angle.
  • SwerveModulePosition: WPILib representation of one module's traveled distance and current angle for pose tracking.
  • SwerveDrivetrain: CTRE's drivetrain class that owns the Phoenix 6 swerve control and pose estimation behavior.
  • CommandSwerveDrivetrain: the generated command-based wrapper we use in robot code.

4. Constants

Swerve constants must be boring and correct. Most "swerve code bugs" are actually constants bugs. In our CTRE format, students should usually edit the generated constants instead of inventing a new constants layout.

// Example shape, not complete robot code
private static final int kPigeonId = 0;
private static final String kCANBus = "rio";

private static final int kFrontLeftDriveMotorId = 1;
private static final int kFrontLeftSteerMotorId = 2;
private static final int kFrontLeftEncoderId = 3;
private static final double kFrontLeftEncoderOffset = 0.237;

private static final double kFrontLeftXPosMeters = 0.31;
private static final double kFrontLeftYPosMeters = 0.31;

5. Module Configuration

In a fully custom swerve, you might write your own module class. In our CTRE format, module behavior is usually described through generated SwerveModuleConstants and CTRE owns most of the low-level module control.

  • Drive motor ID: the TalonFX that spins the wheel.
  • Steer motor ID: the TalonFX that turns the module.
  • Encoder ID: the CANcoder that reports the absolute steering angle.
  • Encoder offset: the calibration value that makes "module zero" match the real wheel direction.
  • X and Y position: the module's location from the robot center, in meters.
  • Inversions: drive and steer direction settings that must match the real wiring and gearing.

6. Teleop Driving With Requests

Instead of manually calling setDesiredState on each module during teleop, our CTRE-based format usually creates a drive request and passes it to the drivetrain.

// Example idea, names may differ in the generated project
private final SwerveRequest.FieldCentric driveRequest =
    new SwerveRequest.FieldCentric()
        .withDeadband(kMaxSpeed * 0.1)
        .withRotationalDeadband(kMaxAngularRate * 0.1);

drive.applyRequest(() -> driveRequest
    .withVelocityX(-driverController.getLeftY() * kMaxSpeed)
    .withVelocityY(-driverController.getLeftX() * kMaxSpeed)
    .withRotationalRate(-driverController.getRightX() * kMaxAngularRate)
);

This is still the same idea as normal swerve: joystick input becomes desired chassis movement. CTRE's API handles the module-level control path.

7. Field-Relative Driving

In robot-relative driving, pushing the joystick forward means "drive toward the robot's front." In field-relative driving, pushing forward means "drive away from the driver station" no matter which way the robot is facing.

The CTRE field-centric request uses the drivetrain's heading information to do this. Field-relative driving is easier for drivers, but only if the gyro direction, operator perspective, and zero heading are correct.

8. Drivetrain Subsystem Flow

  1. Read joystick x, y, and rotation.
  2. Apply deadband and speed scaling.
  3. Choose a CTRE request type, usually field-centric for driver control.
  4. Apply the request to CommandSwerveDrivetrain.
  5. Let CTRE's swerve API handle module states, optimization, and closed-loop control.
  6. Use the drivetrain pose estimate for autonomous, logging, and driver assist.

9. Odometry And Pose

Pose estimation tracks the robot pose by combining gyro heading and module movement. In CTRE's Phoenix 6 swerve API, the drivetrain includes built-in pose estimation behavior, which is required for autonomous path following and useful for driver assist features.

  • Gyro: provides robot heading.
  • Module positions: provide how far each wheel traveled and what direction it pointed.
  • Reset pose: autonomous must start from the same pose the code believes.
  • Vision: later, AprilTags can help correct drift, but basic drivetrain pose should work first.

10. Common Swerve Bugs

  • Wrong module order: front-left code controls the front-right hardware.
  • Bad absolute offsets: modules point slightly wrong even when the code looks right.
  • Gyro sign reversed: field-relative drive rotates the controls the wrong way.
  • Mixed units: rotations, radians, degrees, meters, and meters per second get mixed together.
  • Wrong generated constants: a Tuner X project can only be correct if the robot measurements and IDs entered into it are correct.
  • Skipping module tests: trying to debug all four modules at once makes simple mistakes hard to see.

What To Edit First

When using the team swerve format, start with the generated constants and drivetrain request code. Do not rewrite the CTRE swerve internals unless the software lead has a specific reason.

Mission 1

Make a CTRE swerve constants table for a robot. Include Pigeon ID, CAN bus, module name, drive motor ID, steer motor ID, encoder ID, encoder offset, X position, Y position, wheel diameter, drive gear ratio, and steer gear ratio.

Mission 2

Read a generated CommandSwerveDrivetrain and TunerConstants file. Mark which lines describe hardware, which lines describe tuning, and which lines are used by driver controls.

Rule Of Thumb

When debugging swerve, isolate first. Test the generated constants, one module, then four modules on blocks, then slow robot-centric driving, then field-centric driving, then pose estimation, then autonomous.

Reference

Use the official CTRE Phoenix 6 Swerve Overview, Swerve Builder API, and Tuner X Swerve Project Generator docs when working on the real robot.
