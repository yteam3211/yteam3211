Simulation

Simulation lets programmers test robot code without the robot. It will never replace real hardware testing, but it can catch command bugs, unit mistakes, missing requirements, and broken autonomous logic before anyone touches the robot.

The main idea is simple: your normal robot code commands motor voltage, and your simulation code uses that voltage to update fake sensors. Commands should not need to know whether the data came from a real motor controller or a simulated mechanism.

What We Simulate

  • Inputs: Driver controls, sensors, encoders, gyro, and game piece detection.
  • Mechanisms: Flywheels, arms, elevators, drivetrains, and simple state machines.
  • Outputs: Motor voltage, solenoid states, LEDs, and mechanism positions.

The Simulation Loop

  1. Robot code calculates motor output.
  2. The sim reads the voltage that would have gone to the motor.
  3. A WPILib sim class updates the fake mechanism physics.
  4. The sim writes fake sensor values back into the robot code.
  5. Commands read those fake sensors just like real sensors.
@Override
public void simulationPeriodic() {
    // 1. Send motor voltage into the physics model.
    mechanismSim.setInputVoltage(appliedVolts);

    // 2. Advance the model by one robot loop.
    mechanismSim.update(0.02);

    // 3. Copy simulated position/velocity into sensor variables.
    simulatedPosition = mechanismSim.getPosition();
}

Useful WPILib Simulation Classes

  • DCMotorSim for a simple motor gearbox with position and velocity.
  • FlywheelSim for shooters and spinning wheels.
  • SingleJointedArmSim for arms.
  • ElevatorSim for elevators.

1. DCMotorSim

DCMotorSim is the general-purpose simulation for a motor attached to a mechanism. Use it when the mechanism is not specifically a flywheel, arm, elevator, or drivetrain.

It gives you angular position and angular velocity. This is useful for simple rollers, wheels, and test mechanisms.

import edu.wpi.first.math.system.plant.DCMotor;
import edu.wpi.first.math.system.plant.LinearSystemId;
import edu.wpi.first.wpilibj.simulation.DCMotorSim;

private final DCMotorSim motorSim = new DCMotorSim(
    LinearSystemId.createDCMotorSystem(
        DCMotor.getKrakenX60(1),
        0.01, // Moment of inertia, kg*m^2
        5.0   // Gear ratio
    ),
    DCMotor.getKrakenX60(1)
);

public void simulationPeriodic() {
    motorSim.setInputVoltage(appliedVolts);
    motorSim.update(0.02);

    double positionRadians = motorSim.getAngularPositionRad();
    double velocityRadPerSec = motorSim.getAngularVelocityRadPerSec();
}

What each part means:

  • DCMotor.getKrakenX60(1) describes the motor model.
  • 0.01 is the mechanism inertia. A bigger number accelerates more slowly.
  • 5.0 is the gear ratio. Higher gearing changes speed and torque behavior.
  • setInputVoltage is how your simulated motor output enters the physics model.
  • update(0.02) advances the model by one normal 20 ms robot loop.

2. FlywheelSim

FlywheelSim is for mechanisms where the main thing you care about is speed. Shooters are the classic example.

import edu.wpi.first.math.system.plant.DCMotor;
import edu.wpi.first.wpilibj.simulation.FlywheelSim;

private final FlywheelSim shooterSim = new FlywheelSim(
    DCMotor.getKrakenX60(1),
    1.5,  // Gear ratio
    0.02  // Moment of inertia, kg*m^2
);

public void simulationPeriodic() {
    shooterSim.setInputVoltage(shooterVolts);
    shooterSim.update(0.02);

    double shooterVelocityRadPerSec =
        shooterSim.getAngularVelocityRadPerSec();
}

How to think about it: a flywheel does not need a "position goal" most of the time. It needs to reach and hold a velocity. Feedforward matters a lot here because a spinning wheel needs continuous voltage to stay at speed.

3. SingleJointedArmSim

SingleJointedArmSim models an arm rotating around one pivot. It includes gravity, which is why arms behave differently from normal motors.

import edu.wpi.first.math.system.plant.DCMotor;
import edu.wpi.first.wpilibj.simulation.SingleJointedArmSim;

private final SingleJointedArmSim armSim = new SingleJointedArmSim(
    DCMotor.getKrakenX60(1),
    60.0,  // Gear ratio
    SingleJointedArmSim.estimateMOI(0.6, 4.0),
    0.6,   // Arm length, meters
    Math.toRadians(-70),
    Math.toRadians(90),
    true,  // Simulate gravity
    Math.toRadians(0)
);

public void simulationPeriodic() {
    armSim.setInputVoltage(armVolts);
    armSim.update(0.02);

    double armAngleRadians = armSim.getAngleRads();
    double armVelocityRadPerSec = armSim.getVelocityRadPerSec();
}

What each part means:

  • 60.0 is the gear ratio between motor and arm.
  • estimateMOI(0.6, 4.0) estimates how hard the arm is to rotate from length and mass.
  • The min and max angles act like physical stops.
  • true turns on gravity simulation.

4. ElevatorSim

ElevatorSim models a vertical linear mechanism. This is useful for elevators, lifts, and anything that moves straight up and down.

import edu.wpi.first.math.system.plant.DCMotor;
import edu.wpi.first.wpilibj.simulation.ElevatorSim;

private final ElevatorSim elevatorSim = new ElevatorSim(
    DCMotor.getKrakenX60(1),
    12.0, // Gear ratio
    5.0,  // Carriage mass, kg
    0.03, // Drum radius, meters
    0.0,  // Minimum height, meters
    1.2,  // Maximum height, meters
    true, // Simulate gravity
    0.0   // Starting height, meters
);

public void simulationPeriodic() {
    elevatorSim.setInputVoltage(elevatorVolts);
    elevatorSim.update(0.02);

    double heightMeters = elevatorSim.getPositionMeters();
    double velocityMetersPerSecond = elevatorSim.getVelocityMetersPerSecond();
}

How to think about it: elevators need position limits and zeroing logic. The sim can help you check that commands stop at the top and bottom before testing on the robot.

5. LinearSystemSim

LinearSystemSim is the base class underneath several WPILib mechanism sims. New students usually should not start here. Use the specific classes first: DCMotorSim, FlywheelSim, SingleJointedArmSim, and ElevatorSim.

Connecting Sim To A Subsystem

The cleanest pattern is to make real hardware and simulated hardware provide the same data to the subsystem. Later, this also connects nicely to AdvantageKit IO layers.

public class ShooterIOInputs {
    public double velocityRadPerSec;
    public double appliedVolts;
}

public interface ShooterIO {
    void updateInputs(ShooterIOInputs inputs);
    void setVoltage(double volts);
}

The real implementation reads the motor controller. The sim implementation uses FlywheelSim. The subsystem can use either one without changing command code.

Units In Simulation IO Interfaces

Typed units are useful at the subsystem boundary because they make commands harder to call incorrectly. The sim implementation can convert those units into the raw doubles that WPILib simulation classes expect.

import static edu.wpi.first.units.Units.*;

import edu.wpi.first.math.system.plant.DCMotor;
import edu.wpi.first.units.measure.Angle;
import edu.wpi.first.units.measure.Voltage;
import edu.wpi.first.wpilibj.simulation.SingleJointedArmSim;

public interface ArmIO {
    public static class ArmIOInputs {
        public Angle position = Degrees.zero();
        public double velocityRadPerSec = 0.0;
        public Voltage appliedVoltage = Volts.zero();
    }

    default void updateInputs(ArmIOInputs inputs) {}
    default void setVoltage(Voltage volts) {}
    default void goToPosition(Angle position) {}
    default void holdPosition() {}
    default void stop() {}
}

public class ArmIOSim implements ArmIO {
    private final SingleJointedArmSim sim = new SingleJointedArmSim(
        DCMotor.getKrakenX60(1),
        60.0,
        SingleJointedArmSim.estimateMOI(0.6, 4.0),
        0.6,
        Math.toRadians(-70),
        Math.toRadians(90),
        true,
        0.0
    );

    private Voltage appliedVoltage = Volts.zero();

    @Override
    public void updateInputs(ArmIOInputs inputs) {
        sim.setInputVoltage(appliedVoltage.in(Volts));
        sim.update(0.02);

        inputs.position = Radians.of(sim.getAngleRads());
        inputs.velocityRadPerSec = sim.getVelocityRadPerSec();
        inputs.appliedVoltage = appliedVoltage;
    }

    @Override
    public void setVoltage(Voltage volts) {
        appliedVoltage = volts;
    }

    @Override
    public void goToPosition(Angle position) {
        double goalRadians = position.in(Radians);
        // A real version would calculate PID voltage from this goal.
    }
}

Good pattern: use units in the subsystem API, then convert to raw doubles inside the IO implementation when a simulation class, motor controller, or sensor API requires it.
