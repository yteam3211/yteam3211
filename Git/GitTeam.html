Git for Teams

Before we dive into how to use Git as a team, let's look at how Git manages files.

Git stores files in a branching system (often visualized as a tree). It starts from a main or master branch, which serves as the stable source of truth. From there, you can create separate branches for specific tasks.

Git Branching

A Git branch's primary job is to provide a safe, isolated sandbox for your code. It allows you to work on a specific task—like building a new robot subsystem or fixing a bug—without affecting the "clean" code that you know already works.

By using a branch, you can:

  • Commit your progress regularly.
  • Switch back and forth between different tasks (e.g., jumping from feature development to an urgent fix).
  • Combine your new code with the main project only after you have verified it doesn't break anything.

Pull Requests (PR)

A Pull Request is a formal proposal to merge your branch's code into the main branch. It acts as a review gate:

  • Notification: It notifies your teammates that your feature is ready.
  • Transparency: It displays exactly which lines of code were changed.
  • Collaboration: It provides a space for "code reviews," where others can check for bugs, suggest improvements, and ensure the code meets the team's standards before it is officially merged.

Issues

Issues are the primary way we track tasks, bugs, and feature requests.

  • Creation: You can create an issue via the "Issues" tab in the repository by clicking "New Issue."
  • Management: You can assign issues to team members, add labels (like bug or enhancement), and update the status as you work.
  • Resolution: Once the task is complete, the issue can be closed (resolved).

GitHub Projects

We use GitHub Projects as a Kanban-style board to organize our workflow. It allows the team to see exactly what is "To Do," "In Progress," and "Done" by linking directly to the Issues and Pull Requests mentioned above.
