Sensors

Sensors are how robot code learns what is happening in the real world. Without sensors, commands can only guess. With sensors, the robot can close loops, zero mechanisms, detect game pieces, and drive accurately.

The most important habit with sensors is to always ask what the number means. A sensor value is only useful when you know the physical unit, where zero is, what direction is positive, and what the robot should do if the reading is wrong.

Relative Encoders

Measure how far something has moved since startup or since the code last reset the position.

Absolute Encoders

Measure a real mechanism angle even after the robot reboots.

Gyros

Measure robot heading and rotation rate. Drivetrain code depends on this for field-relative driving and auto paths.

Limit Switches

Detect hard mechanism endpoints and help safely zero arms, elevators, and climbers.

Beam Breaks

Detect game pieces in intakes, indexers, and shooters.

Distance Sensors

Measure how far the robot or mechanism is from an object.

Vision

Detect targets, estimate robot pose, and help line up to field elements.

1. Relative Encoders

A relative encoder measures movement from a starting point. TalonFX motors have built-in relative encoders, so you can read motor position and velocity without adding another sensor.

  • Used for: flywheels, drivetrain wheels, elevators, and any mechanism where motor movement tells you mechanism movement.
  • Common units: motor rotations, mechanism rotations, meters, degrees, radians, rotations per second, or meters per second.
  • Important problem: after reboot, a relative encoder does not automatically know the real mechanism position.
// Example idea: convert motor rotations to mechanism rotations
double mechanismRotations = motorRotations / gearRatio;

2. Absolute Encoders

An absolute encoder reports a real position within one full rotation. If an arm is at 35 degrees when the robot turns on, the absolute encoder can tell you that immediately.

  • Used for: arms, wrists, swerve module steering, and mechanisms that must know their angle at boot.
  • Common units: rotations from 0 to 1, degrees from 0 to 360, or radians from 0 to 2 pi.
  • Important problem: you usually need an offset so sensor zero matches mechanism zero.
// Example idea: apply an offset to make sensor zero match the robot
double armDegrees = absoluteEncoderDegrees - armZeroOffsetDegrees;

3. Gyros

A gyro measures robot rotation. In FRC, this is usually the sensor that tells code which way the robot is facing on the field.

  • Used for: field-relative driving, auto path following, balancing, turning to angles, and pose estimation.
  • Common units: degrees or radians.
  • Important problem: teams must agree on clockwise vs. counterclockwise and when the heading is reset.
// Example idea: zero heading before a match or at a known pose
gyro.reset();

4. Limit Switches

A limit switch is a simple digital sensor. It is either pressed or not pressed. This makes it extremely useful for safety and zeroing.

  • Used for: elevator bottom detection, climber end stops, intake deployed position, and homing routines.
  • Common units: boolean values: true or false.
  • Important problem: wiring can be normally open or normally closed, so check whether true means pressed or released.
if (bottomLimitSwitch.get()) {
    elevatorEncoder.setPosition(0.0);
}

5. Beam Breaks

A beam break uses light to detect whether something is blocking the beam. In robot code, it is usually treated like a boolean sensor.

  • Used for: detecting notes/game pieces, checking if an intake is full, indexing, and shooter readiness.
  • Common units: boolean values: object present or object missing.
  • Important problem: some sensors return false when blocked, so name your variables clearly.
boolean hasGamePiece = !beamBreak.get();

6. Distance Sensors

Distance sensors estimate how far away something is. They can be useful, but they are often noisier than new programmers expect.

  • Used for: detecting objects, measuring mechanism position without contact, and simple alignment checks.
  • Common units: millimeters, centimeters, meters, or inches.
  • Important problem: readings can change depending on surface color, angle, lighting, and reflections.

7. Vision

Vision systems use cameras to detect field targets, AprilTags, retroreflective tape, or game pieces. Vision is powerful, but it should not be treated like magic truth.

  • Used for: aiming, robot pose estimation, auto alignment, and finding game pieces.
  • Common units: target angle, target distance, robot pose, latency, and confidence.
  • Important problem: vision has delay. Always think about when the image was captured, not just when the robot code received it.

Sensor Questions To Ask

  • What physical thing does this sensor measure?
  • What unit does the code use?
  • Does the sensor need to be zeroed?
  • What should happen if the sensor is unplugged or wrong?
  • Can the robot safely move if this sensor is lying?
  • Should this value be logged for debugging?
