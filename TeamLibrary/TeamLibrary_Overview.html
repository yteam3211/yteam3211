FrcCatalyst Team Library

FrcCatalyst is the team library we use to create common FRC mechanisms faster. Instead of writing every motor controller, PID loop, feedforward, simulation model, telemetry path, and safety check from scratch, students configure a mechanism with a builder.

This chapter comes after WPILib, CTRE, simulation, and AdvantageKit because FrcCatalyst combines ideas from all of them. It is easier to trust the library when you understand what it is doing underneath.

Generator Tool

Use the local FRC Catalyst Subsystem Generator to create starter Java snippets. The generator is connected to the mechanism builder calls in the FrcCatalyst GitHub repo.

What FrcCatalyst Gives Us

  • Mechanism builders: Configure elevators, arms, shooters, rollers, climbers, claws, pneumatics, and differential wrists.
  • Telemetry: Mechanism data is published in a predictable Catalyst layout for debugging.
  • Simulation support: Mechanisms can use physical data such as motor type, gearing, mass, radius, and moment of inertia.
  • Safety checks: Current limits, temperature limits, limit switches, and stall detection are part of the config instead of scattered across code.
  • Command helpers: Mechanisms expose commands like holding position or moving to named positions.

Mechanism Map

  • LinearMechanism: elevators, slides, and telescoping mechanisms.
  • RotationalMechanism: arms, wrists, turrets, hoods, and pivots.
  • FlywheelMechanism: shooters and accelerator wheels.
  • RollerMechanism: intakes, conveyors, and indexers.
  • WinchMechanism: climbers and rope/spool systems.
  • ClawMechanism: motor-driven grippers with stall or beam-break detection.
  • PneumaticMechanism: single or double solenoid mechanisms.
  • DifferentialWristMechanism: two-motor wrists with pitch and roll control.

Basic Workflow

  1. Choose the mechanism type that matches the real robot part.
  2. Open the FRC Catalyst Subsystem Generator.
  3. Enter CAN IDs, motor type, gearing, limits, PID, feedforward, and named positions.
  4. Copy the generated Java instance into the robot project.
  5. Bind the mechanism commands in RobotContainer.
  6. Test in simulation, then tune carefully on the real robot.

Example: Elevator

A Catalyst elevator starts as one builder config. The important part is that every number should come from the real mechanism or from a tuning decision.

import frc.lib.catalyst.hardware.MotorType;
import frc.lib.catalyst.mechanisms.LinearMechanism;

private final LinearMechanism elevator = new LinearMechanism(
    LinearMechanism.Config.builder()
        .name("Elevator")
        .motor(13)
        .follower(14, true)
        .motorType(MotorType.KRAKEN_X60)
        .gearRatio(10.0)
        .drumRadius(0.0254)
        .range(0.0, 1.2)
        .mass(5.0)
        .pid(50.0, 0.0, 0.5)
        .gravityGain(0.35)
        .motionMagic(2.0, 4.0, 20.0)
        .currentLimit(40)
        .reverseLimitSwitch(0, true)
        .maxTemperature(70)
        .position("STOW", 0.0)
        .position("AMP", 0.8)
        .position("HIGH", 1.1)
        .build()
);

What each group means:

  • motor, follower, and motorType describe the hardware.
  • gearRatio, drumRadius, range, and mass describe the physical elevator.
  • pid, gravityGain, and motionMagic describe how the elevator should move.
  • currentLimit, reverseLimitSwitch, and maxTemperature protect the robot.
  • position creates named goals that commands can use later.

Using The Mechanism

Once the mechanism exists, students should use its commands from RobotContainer instead of manually setting motor power everywhere.

private void configureBindings() {
    elevator.setDefaultCommand(elevator.holdPosition());

    operatorController.a().onTrue(elevator.goTo("AMP"));
    operatorController.b().onTrue(elevator.goTo("HIGH"));
    operatorController.x().onTrue(elevator.goTo("STOW"));
}

Why this matters: commands describe robot actions. The mechanism config owns the motor details, limits, tuning, and safety behavior.

How To Use The Generator

  • Mechanism: Pick the real mechanism type first. Do not force an arm into an elevator config.
  • Catalyst name: Use the same name drivers and programmers use, such as Elevator, Arm, or Intake.
  • Builder calls: Fill in the values you know. Leave unknown tuning values conservative until testing.
  • Named positions: Use clear names like STOW, INTAKE, AMP, and HIGH.
  • Followers: Add follower motors only when the physical mechanism really has them.
  • Generated Java: Copy the snippet, then clean up imports and constants in the robot project.

Good Team Rules

  • Do not use FrcCatalyst as magic. Know what mechanism, motor, sensor, and control loop it represents.
  • Put CAN IDs and important physical constants in one clear location.
  • Start with safe limits before tuning for speed.
  • Test named positions one at a time.
  • Commit working configs after each successful tuning step.
  • When the generator output does not compile, fix the page or the snippet instead of silently rewriting the library pattern.
