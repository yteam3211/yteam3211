AdvantageKit

AdvantageKit is an advanced logging and replay framework. The important idea is that robot code should read inputs, record them, produce outputs, and be able to replay the same inputs later in simulation.

The biggest change for new students is the IO layer. Instead of a subsystem reading motor controllers directly, the subsystem asks an IO object for sensor data. AdvantageKit logs that sensor data so the same subsystem code can be replayed later without the robot.

The Big Pattern

  • Inputs: Sensor and hardware data collected from an IO layer.
  • Outputs: Motor commands and subsystem state decisions.
  • Replay: Running robot code again from a log to debug without the robot.
  • AdvantageScope: A tool for graphing logs and visualizing robot state.

Why This Comes Late

AdvantageKit is powerful, but it makes more sense after students understand subsystems, commands, sensors, simulation, and logging. Otherwise the IO-layer pattern feels like ceremony instead of a debugging superpower.

1. The IO Interface

An IO interface is the border between subsystem logic and hardware. The subsystem calls methods like setVoltage, while the IO implementation handles the real motor controller, simulated motor, or replayed log data.

public interface ShooterIO {
    default void updateInputs(ShooterIOInputs inputs) {}
    default void setVoltage(double volts) {}
    default void setTargetVelocity(double velocityRadPerSec) {}
    default void stop() {}
}

What each part means:

  • ShooterIO describes what the subsystem needs from the hardware layer.
  • updateInputs copies all sensor values into one inputs object once per robot loop.
  • setVoltage is an output command. It tells the IO layer what the subsystem wants the motor to do.
  • setTargetVelocity is another output command. A real IO class might pass this into a motor controller velocity request.
  • stop gives every implementation a clear way to turn the mechanism off.
  • The empty default methods make it easy to create a dummy IO implementation for simulation or tests.

For a position mechanism, the IO interface can include commands that sound like robot actions instead of raw motor calls.

import edu.wpi.first.units.measure.Angle;
import edu.wpi.first.units.measure.Voltage;

public interface ArmIO {
    default void updateInputs(ArmIOInputs inputs) {}
    default void setVoltage(Voltage volts) {}
    default void goToPosition(Angle position) {}
    default void holdPosition() {}
    default void stop() {}
}

Why this style helps: goToPosition tells the hardware layer what the subsystem wants, but it does not force the subsystem to know whether the IO class uses a TalonFX closed loop, a WPILib PIDController, or a simulation model.

2. The Inputs Class

The inputs class stores every value the subsystem reads from hardware. For a shooter, that might be motor velocity, applied voltage, current, temperature, and whether the motor controller is connected.

import org.littletonrobotics.junction.AutoLog;

public interface ShooterIO {
    @AutoLog
    public static class ShooterIOInputs {
        public double velocityRadPerSec = 0.0;
        public double appliedVolts = 0.0;
        public double currentAmps = 0.0;
        public boolean connected = true;
    }

    void updateInputs(ShooterIOInputs inputs);
    void setVoltage(double volts);
}

What each field means:

  • velocityRadPerSec is sensor data from the encoder.
  • appliedVolts is the voltage actually sent to the motor.
  • currentAmps helps find jams, bad gearing, or a motor working too hard.
  • connected is useful for alerts when a CAN device is missing.

3. @AutoLog

@AutoLog tells AdvantageKit to generate a second class with logging support. If the class is named ShooterIOInputs, the generated class is named ShooterIOInputsAutoLogged.

private final ShooterIOInputsAutoLogged inputs =
    new ShooterIOInputsAutoLogged();

Use the generated AutoLogged class in the subsystem, not the original inputs class. AdvantageKit uses that generated class to save inputs to the log and load them back during replay.

Important Rule

Everything the subsystem reads from hardware should go inside the inputs class. If a sensor value is read directly in the subsystem and never logged, replay will not be able to reproduce that behavior.

4. Units In AdvantageKit Inputs

AdvantageKit can log measure values in inputs classes, but many teams still choose simple doubles with unit names in the field. Both styles can work. The important part is to be consistent.

import static edu.wpi.first.units.Units.*;

import edu.wpi.first.units.measure.Angle;
import edu.wpi.first.units.measure.AngularVelocity;
import edu.wpi.first.units.measure.Current;
import edu.wpi.first.units.measure.Voltage;
import org.littletonrobotics.junction.AutoLog;

@AutoLog
public static class ArmIOInputs {
    public Angle position = Degrees.zero();
    public AngularVelocity velocity = RadiansPerSecond.zero();
    public Voltage appliedVoltage = Volts.zero();
    public Current current = Amps.zero();

    // Also acceptable if your team prefers raw log fields:
    public double positionRad = 0.0;
    public double currentAmps = 0.0;
}

Team rule suggestion: if a field is a raw double, put the unit in the name, such as positionRad, heightMeters, or currentAmps.

5. Real IO Implementation

The real IO class talks to actual hardware. It reads motor controller values in updateInputs and applies commands in methods like setVoltage.

public class ShooterIOTalonFX implements ShooterIO {
    private final TalonFX motor = new TalonFX(10);

    @Override
    public void updateInputs(ShooterIOInputs inputs) {
        inputs.velocityRadPerSec =
            motor.getVelocity().getValueAsDouble() * 2.0 * Math.PI;
        inputs.appliedVolts = motor.getMotorVoltage().getValueAsDouble();
        inputs.currentAmps = motor.getStatorCurrent().getValueAsDouble();
        inputs.connected = motor.isConnected();
    }

    @Override
    public void setVoltage(double volts) {
        motor.setVoltage(volts);
    }
}

How to think about it: this class is allowed to know about TalonFX, SparkMax, CANcoder, gyros, and other hardware. The subsystem should not need to know those details.

6. Sim IO Implementation

The sim IO class uses WPILib simulation classes instead of real hardware. It still fills in the same inputs object, so the subsystem does not care whether the data came from a real robot or a simulation.

public class ShooterIOSim implements ShooterIO {
    private final FlywheelSim sim =
        new FlywheelSim(DCMotor.getKrakenX60(1), 1.5, 0.02);

    private double appliedVolts = 0.0;

    @Override
    public void updateInputs(ShooterIOInputs inputs) {
        sim.setInputVoltage(appliedVolts);
        sim.update(0.02);

        inputs.velocityRadPerSec = sim.getAngularVelocityRadPerSec();
        inputs.appliedVolts = appliedVolts;
        inputs.currentAmps = sim.getCurrentDrawAmps();
        inputs.connected = true;
    }

    @Override
    public void setVoltage(double volts) {
        appliedVolts = MathUtil.clamp(volts, -12.0, 12.0);
    }
}

Why this is useful: commands, PID, feedforward, and alerts can all run against simulated inputs before the robot exists.

7. Logger.processInputs

Every subsystem should update and process inputs once per loop. This usually happens at the start of periodic.

public class Shooter extends SubsystemBase {
    private final ShooterIO io;
    private final ShooterIOInputsAutoLogged inputs =
        new ShooterIOInputsAutoLogged();

    private double targetRadPerSec = 0.0;

    public Shooter(ShooterIO io) {
        this.io = io;
    }

    @Override
    public void periodic() {
        io.updateInputs(inputs);
        Logger.processInputs("Shooter", inputs);

        Logger.recordOutput("Shooter/TargetRadPerSec", targetRadPerSec);
        Logger.recordOutput("Shooter/AtSetpoint", atSetpoint());
    }

    public void setVoltage(double volts) {
        io.setVoltage(volts);
    }
}

What each Logger call does:

  • Logger.processInputs("Shooter", inputs) records all shooter inputs under the Shooter table.
  • During replay, processInputs can load the old logged values back into inputs.
  • Logger.recordOutput records values calculated by robot code, like setpoints, command states, and debugging numbers.

8. Starting The Logger

The logger is usually configured in Robot.robotInit. Metadata and data receivers must be added before Logger.start().

import org.littletonrobotics.junction.Logger;
import org.littletonrobotics.junction.networktables.NT4Publisher;
import org.littletonrobotics.junction.wpilog.WPILOGWriter;

@Override
public void robotInit() {
    Logger.recordMetadata("ProjectName", "YTeamTrainingRobot");

    Logger.addDataReceiver(new WPILOGWriter());
    Logger.addDataReceiver(new NT4Publisher());

    Logger.start();

    robotContainer = new RobotContainer();
}

What this does:

  • recordMetadata saves information about the code version, robot name, or event.
  • WPILOGWriter writes log files that can be opened in AdvantageScope.
  • NT4Publisher publishes live data over NetworkTables so AdvantageScope can see it while the robot runs.
  • Logger.start() begins logging. Add receivers before this line.

9. Inputs vs Outputs

  • Input: Something measured or received from outside robot code. Examples: encoder position, gyro angle, beam break state, motor current.
  • Output: Something robot code decides or calculates. Examples: target velocity, chosen command state, PID error, desired arm angle.
  • Use processInputs for inputs. This makes replay possible.
  • Use recordOutput for outputs. This makes debugging easier, but outputs are not the source of replay.

Mission 1

Take one subsystem you already understand and list every value that should go inside its inputs class. Separate sensor data from calculated outputs.

Mission 2

Write the IO interface for an arm, elevator, or intake. Include an @AutoLog inputs class, updateInputs, and at least one output method.
