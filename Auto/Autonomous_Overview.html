Autonomous With PathPlanner

PathPlanner is the tool we use to design and run autonomous routines. Instead of writing every auto movement by hand, we draw paths on the field, connect robot commands to points in the path, and let PathPlannerLib generate the command that follows the plan.

The important idea is this: PathPlanner does not replace robot code. It connects to robot code. The drivetrain still needs odometry, a gyro, wheel/module states, and a correctly configured AutoBuilder.

1. What PathPlanner Needs From The Robot

PathPlanner can only follow a path if your drivetrain can answer these questions:

  • Where am I? The robot pose from odometry or pose estimation.
  • How fast am I moving? Chassis speeds or module states.
  • How do I drive? A method that accepts target speeds and sends outputs to the drivetrain.
  • How do I reset pose? A method that sets the robot pose to the auto starting pose.
  • Which alliance am I on? So paths can be mirrored correctly when needed.

2. AutoBuilder

AutoBuilder is the bridge between your drivetrain code and PathPlanner. You configure it once, usually from the drivetrain or RobotContainer, then PathPlanner can build commands for paths and autos.

// Simplified idea, not a complete drivetrain config
AutoBuilder.configure(
    drive::getPose,
    drive::resetPose,
    drive::getRobotRelativeSpeeds,
    drive::driveRobotRelative,
    controllerConfig,
    shouldFlipPath,
    drive
);

If AutoBuilder is wrong, every auto will be wrong. Start debugging there before blaming the path.

3. Following One Path

The smallest PathPlanner test is a single path. This is useful before building a full auto because it checks that the drivetrain can follow the planned movement.

PathPlannerPath path = PathPlannerPath.fromPathFile("Test Path");
Command followPath = AutoBuilder.followPath(path);

Test one simple path first: drive forward one or two meters. If that does not work, a complex multi-piece auto will not work either.

4. Building A Full Auto

A full auto can contain paths, waits, and commands. PathPlanner stores these in deploy files, and the robot loads them by name.

Command auto = new PathPlannerAuto("Center Start 2 Piece");

For driver selection, use an auto chooser so the drive team can pick the routine on the dashboard before the match.

5. Named Commands

Named commands let the PathPlanner GUI trigger real robot commands. For example, the path can tell the robot to intake while driving, shoot at a marker, or stow an arm before the next path.

NamedCommands.registerCommand("Intake", new IntakeCommand(intake));
NamedCommands.registerCommand("Shoot", new ShootCommand(shooter));
NamedCommands.registerCommand("Stow", new StowArmCommand(arm));

Register named commands before loading autos. If the names do not match exactly, the auto may skip the action or fail.

6. PathPlanner Uses

  • Simple autonomous: leave the starting area or drive to a scoring location.
  • Multi-piece autonomous: score, drive to a game piece, intake, return, and score again.
  • Auto alignment: generate or follow a route to a field target.
  • Mechanism timing: start spinning a shooter before the robot reaches the shot location.
  • Driver assist: use pathfinding or short paths to help drivers line up.
  • Simulation testing: verify pose movement and command timing without the robot.

7. Common PathPlanner Mistakes

  • Wrong starting pose: the robot starts somewhere different from where the auto thinks it starts.
  • Gyro direction is reversed: paths curve or rotate the wrong way.
  • Bad units: drivetrain code mixes meters, rotations, degrees, or radians.
  • Autos not deployed: the robot does not have the path files in the deploy folder.
  • Named command mismatch: the GUI name and Java registered name are not identical.
  • Command requirements conflict: an event command interrupts the path because both require the drivetrain.
  • No testing space: the path is too fast or too long for the available area.

8. Debugging Checklist

  1. Test drivetrain driving manually first.
  2. Verify gyro heading direction.
  3. Verify odometry moves correctly when the robot moves.
  4. Follow a short straight path.
  5. Follow a short curved path.
  6. Add one named command.
  7. Build the full auto only after the small tests pass.
  8. Log pose, setpoint pose, chassis speeds, and active command names.
